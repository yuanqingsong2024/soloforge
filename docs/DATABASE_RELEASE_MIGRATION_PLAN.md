# SoloForge 数据库与升级方案

## 1. 数据边界

- 开发、测试和用户运行数据库必须分离。
- `prisma/dev.db` 仅用于开发或临时验证，不得打入安装包。
- 用户数据库位于操作系统用户数据目录，路径由主进程统一管理。
- 凭证不进入 SQLite；只保存 Keychain 引用或非敏感元数据。
- 安装包只包含应用代码、迁移资源和必要的 locale，不包含用户数据。

## 2. 迁移责任

推荐由主进程在首次启动和升级时负责：

1. 确认数据目录和数据库文件。
2. 创建安全备份或快照。
3. 检查当前 schema 版本。
4. 以离线方式执行已提交的 Prisma migration。
5. 校验关键表、索引和约束。
6. 迁移成功后启动 API 和 renderer。
7. 失败则停止业务服务，保留备份和诊断日志。

如果暂不在应用启动时自动迁移，必须提供受控的离线迁移工具和清晰的升级前置步骤；不能让用户遇到隐式 schema 不兼容。

## 3. 发布前迁移验证

每个候选版本执行三类验证：

### 从零重放

在空临时数据库执行完整 migration 链，确认成功并运行 Prisma schema 校验。

### 旧版本升级

使用上一内部版本创建真实数据，升级到当前版本，检查：

- 工单、Agent、Role、Tool、Approval、AuditLog 数据完整
- 外键和索引可用
- 敏感字段不被迁移到错误位置
- 应用可以正常启动和查询

### 失败恢复

模拟磁盘不足、数据库锁、损坏 migration 或中断进程：

- 原数据库不被半迁移覆盖
- 备份可恢复
- UI 显示明确错误
- 重试不会重复破坏数据

## 4. 迁移文件规则

- migration 必须随应用代码同一提交提交。
- 目录命名必须唯一、可读、无空后缀或临时名称。
- schema 修改、migration、种子数据和兼容代码必须一起评审。
- 不允许只修改 schema 而遗漏 migration。
- 不允许删除已发布 migration；需要新增向前迁移。
- 每次发布 metadata 附迁移清单、风险和回滚说明。

## 5. 备份与恢复

升级前至少保存：

- SQLite 数据库副本
- 当前应用版本
- migration 状态
- 数据库 hash 和文件大小
- 备份时间与 trace_id

恢复流程：

1. 停止写入和后台任务。
2. 校验备份来源、版本和 hash。
3. 将备份恢复到临时路径。
4. 执行 schema 和关键数据检查。
5. 原子替换当前数据库。
6. 重新启动并执行只读健康检查。

恢复失败不得删除原数据库。导出和恢复属于高危数据操作，必须受审批和审计保护。

## 6. 回滚策略

应用回滚和数据库回滚分开处理：

- 如果仅应用代码有问题，优先回退应用并保留数据库。
- 如果 migration 改变了不可逆结构，必须在发布前准备反向迁移或备份恢复方案。
- 不允许假设旧版本一定能读取新 schema，必须用实际旧版本验证。
- 回滚操作记录 actor、版本、数据库 hash、结果和原因。

## 7. 迁移验收矩阵

| 场景 | 预期 | 阻断 |
|---|---|---:|
| 空库全量迁移 | 成功 | 是 |
| 上一版本升级 | 数据完整、应用可启动 | 是 |
| 重复执行迁移 | 幂等或明确跳过 | 是 |
| 中断后重试 | 不损坏数据库 | 是 |
| 备份恢复 | 数据可读、hash 匹配 | 是 |
| 敏感字段检查 | 无明文凭证 | 是 |
| 旧版本回滚 | 有书面兼容结论 | 是 |

## 8. 证据

发布归档必须包含：

- migration 列表和 Git commit
- 空库及升级日志
- 备份/恢复测试记录
- 数据库 hash
- 失败演练结果
- 已知不可逆变更和回滚说明
