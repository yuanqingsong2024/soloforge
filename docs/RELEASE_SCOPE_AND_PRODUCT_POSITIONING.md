# SoloForge 发布范围与产品定位

> 状态：发布设计基线
> 目标版本：内部稳定版（建议从 `0.1.x` 重新建立版本口径）
> 适用范围：内部使用、受控测试、小型技术团队

## 1. 产品定位

SoloForge 是一个本地优先的 AI Agent 团队操作台：把工单、Agent、工具授权、审批、配置变更、部署和审计放在同一个 Electron 桌面应用中。它的核心价值不是提供新的模型，而是让 Agent 的真实操作具备：

- 明确授权
- 人工审批
- 可追踪执行
- 敏感信息隔离
- 失败可见
- 本地数据可控

## 2. 目标用户与核心场景

### 目标用户

- 个人开发者和技术负责人
- 需要本地运行 Agent 的小型研发团队
- 使用 OpenClaw、Claude Code 或类似运行时的内部团队
- 需要对配置、外发、部署和数据导出保留审批证据的团队

### 本版本必须保证的场景

1. 创建和跟踪工单，状态变化可验证。
2. 管理 Agent、Role、Tool 及其最小权限。
3. 连接并诊断本地或远程 OpenClaw。
4. 对高危动作创建审批，未批准不得执行。
5. 关键动作写入可验证的 append-only 审计日志。
6. 配置变更具备预览、应用结果、回读校验和回滚语义。
7. 备份、恢复和导出不会泄露凭证。
8. 桌面应用可安装、启动、升级和回滚。

## 3. 明确不承诺的能力

本版本不承诺以下能力：

- 公网 SaaS、多租户和自助注册
- 支付、订阅和商业计费
- 自动更新
- 任意 Agent Runtime 的完整兼容
- 所有邮件、Webhook、IM 和第三方渠道的发送能力
- 未经验证的 Claude Code 配置自动应用
- 生产环境的无人值守部署
- 合规认证或外部审计结论

如果某项能力未有真实执行证据，必须在 UI、文档和发布说明中标记为“受限”“禁用”或“未实现”，不得显示为成功。

## 4. 功能状态口径

| 状态 | 含义 | 发布要求 |
|---|---|---|
| 已实现 | 有代码、自动化测试和端到端证据 | 可纳入稳定版 |
| 受限 | 仅支持明确场景或需要手工步骤 | 必须写明限制 |
| 禁用 | 为安全起见不开放执行 | UI 不得伪装为成功 |
| 未实现 | 没有真实执行路径 | 必须 fail-closed |
| 待验证 | 代码存在但尚无发布证据 | 不得作为稳定能力宣传 |

## 5. 范围冻结规则

从发布硬化开始，停止新增页面、Agent Runtime、通讯渠道和商业功能。只允许以下变更：

- P0/P1 发布阻断项修复
- 安全、数据完整性和审计修复
- 测试、构建、签名、安装和回滚能力补齐
- 发布文档和错误提示修正
- 不改变既有数据模型语义的必要兼容性修复

任何新功能必须进入下一版本，不得混入发布候选版本。

## 6. 版本分层

### 开发版

- 可使用测试数据库和 E2E 认证旁路
- 不得用于真实外发、生产部署和合规审计

### 内部候选版（RC）

- 使用干净提交和固定依赖构建
- 所有 P0 阻断项关闭
- 核心测试、安装、迁移和回滚验证通过
- 仅限指定内部用户

### 内部稳定版

- RC 连续观察通过
- 三平台目标制品有可追踪 hash/签名
- 高危动作闭环和数据恢复有证据
- 发布负责人完成 Go 决策

## 7. 当前状态声明

基于当前工作树的已知证据：

- TypeScript 检查通过。
- 单元测试和 Renderer 测试通过。
- 集成测试仍有 2 项失败。
- 当前 `npm run build` 的 electron-builder 阶段失败。
- 工作树存在大量修改和未跟踪文件。
- 出站发送、Claude Code 配置应用和部分审批执行仍存在占位或假成功风险。

因此当前只能标记为**开发版/内部技术预览**，不能标记为内部稳定版。

## 8. 成功标准

SoloForge 达到发布程度的定义是：

> 在一个干净、可追踪的提交上，任何对用户承诺的核心动作都有真实执行结果、失败结果、审批记录和审计证据；安装包可重现，数据库可升级和恢复，安全旁路不会进入正式包，发布人员可以按 Runbook 完成发布和回滚。
