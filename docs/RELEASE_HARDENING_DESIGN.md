# SoloForge 发布硬化技术设计

## 1. 设计原则

- 未实现能力必须失败或禁用，不得返回成功。
- 高危动作先审批，再执行；执行结果与审批结果分离。
- 关键动作没有可靠审计就不执行。
- 本地数据优先，凭证只通过 Keychain/safeStorage 管理。
- 所有失败都必须可见、可定位、可重试或可回滚。

## 2. 出站消息

### 目标状态机

```text
DRAFT -> PENDING_APPROVAL -> APPROVED -> SENDING -> SENT
                                      \-> FAILED -> RETRYING
                                      \-> CANCELLED
```

要求：

- 未批准不得调用外部发送器。
- `SENT` 只能由真实渠道返回成功后写入。
- 超时、网络失败、未知结果不得写 `SENT`，进入 `FAILED` 或 `UNKNOWN`。
- 使用幂等键或内容 hash 防止重试重复发送。
- 每次尝试记录 trace_id、目标掩码、结果和错误分类。
- 真实发送器未接入时，路由必须返回明确的 `not_implemented`/失败状态。

验收：未批准、重复提交、发送失败、重试成功、发送器未配置各有自动化测试。

## 3. 配置应用

配置变更必须执行：

1. 读取并保存 lastKnownGood 快照。
2. 校验 schema、未知字段、敏感字段和写入频率。
3. 生成 diff/patch，必要时进入 `CHANGE_CONFIG` 审批。
4. 调用真实 OpenClaw/Claude Code 配置能力。
5. 回读配置并校验 hash/版本。
6. 成功才更新本地状态；失败保留旧快照并报告原因。
7. 回滚同样走审批和审计。

占位函数不得返回空配置、空 hash 或 `true` 表示成功。若运行时不支持该能力，必须在 UI 和 API 中明确禁用。

## 4. 审批执行

每个高危动作必须注册唯一 handler：

| 动作 | 必须证明 |
|---|---|
| SEND_EXTERNAL | 真实发送结果 |
| MERGE_MAIN | 真实合并结果 |
| DEPLOY_PROD | 真实部署结果 |
| EXPORT_DATA | 导出文件和 hash |
| PURCHASE | 外部交易结果 |
| CHANGE_CONFIG | 回读后的配置状态 |
| ROTATE_TOKEN | 新旧凭证轮换结果 |

找不到 handler 时，执行接口返回失败，不创建“成功”审计。审批记录只说明授权，不等于动作已执行。重复批准、重复执行、越权 actor 和并发决策必须拒绝或幂等。

## 5. 审计可靠性

### 写入策略

- 关键动作使用 fail-closed：审计创建失败时不执行动作。
- 非关键诊断可降级，但必须标记审计缺失并写入本地错误队列。
- 所有记录包含 trace_id、actor、action、before、after、result 和错误分类。
- 敏感字段递归掩码，错误对象也不得带出 token/password/key。
- 只允许 `create`，禁止 update/delete。

### 哈希链

- 使用数据库单调递增序号作为追加顺序，不以时间戳作为唯一顺序。
- 通过事务、进程内互斥或单写入队列避免并发分叉。
- 保存 previousHash 和 currentHash。
- 提供从头验证、断链检测和结果导出能力。
- 增加并发写入、进程重启、相同时间戳和损坏记录测试。

## 6. 认证、CORS 与错误处理

- packaged app 强制拒绝 `SOLOFORGE_E2E=1` 旁路。
- 开发/E2E 旁路只能在明确测试构建中启用。
- 生产 CORS 关闭或只允许应用来源，不使用任意 Origin 反射。
- 有副作用的请求同时校验 Origin、Host、认证 token 和 Content-Type。
- 生产错误响应使用稳定错误码和中文通用消息；详细原因只进脱敏日志。
- 本地 API 继续绑定 `127.0.0.1`，不得默认对外监听。

## 7. 凭证、备份与导出

safeStorage 只保护值，不自动解决容器完整性。凭证文件需要：

- 临时文件写入后原子 rename。
- Unix 权限限制为当前用户可读写。
- 读取时严格校验对象结构和编码。
- 写入串行化，避免并发覆盖。
- 解密全集的调用范围最小化。

备份和导出必须：

- 递归检查 token、password、apiKey、secret、edge token、provider key 等字段。
- 导出前执行 `EXPORT_DATA` 审批。
- 记录文件 hash、大小、时间和 trace_id，不记录敏感内容。
- 恢复前校验格式、版本和路径，禁止路径穿越。
- 恢复失败不破坏当前数据库，优先写入临时库并原子替换。

## 8. 主进程生命周期

启动流程应明确等待顺序：

1. Electron ready。
2. 初始化 Keychain、数据库和迁移。
3. 启动 API 并取得实际端口。
4. 初始化后台服务和离线模式。
5. 创建窗口并注入会话信息。
6. 服务全部就绪后允许 renderer 发起业务请求。

不得在异步窗口创建完成前依赖 `mainWindow` 初始化关键服务。启动失败必须显示可定位诊断，不得静默跳过。

## 9. 发布安全

- 默认关闭自动更新。
- 制品生成 SHA-256；内部环境优先增加代码签名。
- 签名私钥只在发布环境 secret 中使用，不进仓库。
- 离线安装包必须能独立校验来源和 hash。
- 发布记录包含 commit、版本、构建环境、依赖锁文件和迁移清单。

## 10. 技术设计验收

完成硬化后，必须提供：

- 出站状态机和失败重试测试报告
- 配置 apply/回读/回滚报告
- 审批 handler 清单和执行结果报告
- 审计 fail-closed、并发链验证报告
- 认证旁路和 CORS 安全测试报告
- 凭证、备份、导出脱敏报告
- 启动顺序和离线模式冒烟记录
